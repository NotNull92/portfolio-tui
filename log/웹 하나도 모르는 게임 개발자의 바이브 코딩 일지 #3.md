## 🎮 Prologue : 2편에서 예고한 Admin 대시보드, 드디어 착수

2편에서 "다음 편에는 Admin 대시보드 구현과 Vercel 배포로 돌아오겠다. 아마도." 라고 적었다.

그 "아마도"가 10일이나 걸렸다. WITCHDICE 프로토타이핑 챌린지 때문이었다. 6인 인디팀에서 리드 개발자를 맡아서 StateMachine 아키텍처 설계하고, 절차적 맵 생성 시스템 포팅하고, 멀티씬 비동기 전환 시스템 짜느라 정신이 나갈 뻔했다. 뇌의 Update()가 `Time.deltaTime`을 0으로 반환하는 수준이었다.

근데 오늘 드디어 마음을 다잡고 포트폴리오로 돌아왔다. 유니티를 잠시 끄고 VS Code를 켰다. 씬 전환 로딩이 길어서 그런지 심장이 좀 떨렸다.

**"좋아. 오늘은 Admin 대시보드를 만든다."**

## ⚔️ Scene 1 : 화면 전환? 그게 뭔데요?

Admin 대시보드를 만들려면 일단 화면 전환이 필요했다. 터미널 → 포트폴리오 → 관리자 대시보드. 세 개의 화면을 어떻게 왔다 갔다 하지? `Additive` 씬 로딩도 아니고 `Single`도 아닌 그 애매한 느낌.

```jsx
// App.jsx
const [isAuthenticated, setIsAuthenticated] = useState(false);
const [isAdmin, setIsAdmin] = useState(false);
```

상태를 두 개 두면 된다. `isAuthenticated`가 false면 터미널, true면 포트폴리오. 그리고 `isAdmin`이 true면 관리자 대시보드.

유니티로 치면 `SceneManager.LoadScene("AdminScene")` 같은 건데, React에서는 상태 하나만 바꾸면 화면이 알아서 갈아끼워진다. `AnimatePresence` 덕분에 화면 전환 애니메이션도 자동으로 붙는다. `SceneManager`한테 `LoadSceneAsync` 걸어놓고 `allowSceneActivation` 플래그 만지작거리는 그 삽질이 여기선 필요 없다고?

```jsx
<AnimatePresence mode="wait">
  {!isAuthenticated ? (
    <Terminal key="terminal" onAuthenticated={handleAuthenticated} />
  ) : isAdmin ? (
    <AdminDashboard key="admin" onExit={handleExitAdmin} />
  ) : (
    <MainPortfolio key="portfolio" onAdminMode={handleAdminMode} />
  )}
</AnimatePresence>
```

오... 이거 꽤 직관적이다. 유니티에서 씬 전환할 때 `DontDestroyOnLoad` 걸어놓은 매니저 오브젝트에서 상태 관리하는 것과 비슷한데, 훨씬 간단하다. 싱글톤 패턴으로 GameManager 만들어놓고 `Instance == null` 체크하다가 눈 돌아가는 그 루틴이 없다니 감격스럽다.

`onAdminMode` prop을 MainPortfolio에 넘겨서, Admin 비밀번호 인증 성공 시 부모(App)에게 "나 이제 관리자 모드야!" 하고 알려주는 구조다.

**이벤트 시스템? 아, 그냥 콜백 함수구나.** 유니티에서 `Action` 이벤트 델리게이트 쓰는 것과 똑같다. `UnityAction`이니 `System.Action<T>`이니 제네릭 타입 몇 개 넘길지 고민하다가 `UnityEvent`로 바꿀까 말까 하는 그 혼돈의 카오스가 여기선 그냥 `(callback) =>` 끝이다. 이 맛에 웹 하나 보다.

## 💀 Scene 2 : CSS 스크롤 지옥 (뇌가 가비지컬렉터한테 런타임에 수거당한 기분)

이건 오늘 진짜 멘탈이 나간 부분이다. `MissingReferenceException`이 영혼에서 터진 느낌.

포트폴리오 메인 화면에서 탭 내용이 길어지면 스크롤이 안 됐다. 프로젝트 카드가 5개 넘어가면 화면 밖으로 나가버린다. **보이지 않는 프로젝트는 존재하지 않는 것과 같다.** (양자역학의 관측 문제? 아니면 그냥 내 CSS 실력 문제?) `Culling`이 아니라 진짜로 없어지면 어떡하라고.

```
> AI야, tab-container에 스크롤이 안 돼. 뭐가 문제야?
```

AI가 코드를 뜯어보더니 이렇게 말했다.

**"flexbox 체인이 끊어졌습니다."**

...뭐라고? `NullReferenceException: Object reference not set to an instance of an object` 급의 충격이었다.

문제를 요약하면 이렇다. `#root → .app → .portfolio-container → .portfolio-content → .tab-container` 이렇게 flexbox가 중첩되어 있는데, `.app` 클래스에 스타일이 정의되어 있지 않았다. 즉, `height: 100%`가 안 먹혀서 자식들이 "나 몇 픽셀로 해야 돼?" 하고 서로 쳐다보고 있는 상태였다. 부모 RectTransform의 anchor가 설정 안 돼 있는데 자식한테 Stretch하라는 거랑 뭐가 다르냐.

```css
/* .app 클래스가 비어 있었다... */
```

유니티로 치면 Canvas의 RectTransform 세팅이 안 되어 있어서 자식 UI들이 화면 밖으로 날아가는 것과 같다. 레이아웃 그룹(Layout Group)은 있는데 부모의 크기가 0이면 자식도 0이잖아. 똑같은 문제다. `ContentSizeFitter`를 달아도 부모가 `Preferred Size`를 모르면 자식은 그냥 우주 미아다.

```css
html, body, #root, .app {
  height: 100%;
  width: 100%;
}

.app {
  display: flex;
  flex-direction: column;
}
```

이거 한 줄 추가하는 데에 30분이 걸렸다. CSS flexbox, 너는 나의 영원한 숙적이다. 유니티 `LayoutGroup`의 `childForceExpandWidth`보다 더 악질적인 존재.

그리고 스크롤바를 보이지 않게 하되 기능은 유지하고 싶었다.

```css
::-webkit-scrollbar-thumb {
  background: transparent;
}
```

투명 스크롤바. 보이지 않지만 존재한다. 유니티의 `Scrollbar` 컴포넌트를 비활성화하되 `ScrollRect`는 살려둔 것과 같은 느낌. 소름 돋는 은유가 아니라 진짜로 똑같은 상황이었다. `gameObject.SetActive(false)` 하면 안 되고 `CanvasGroup.alpha = 0`으로 해야 하는 그 미묘한 차이.

## 🔥 Scene 3 : Admin 대시보드 구현 (Trello를 클론하다)

이제 본격적으로 Admin 대시보드를 만들었다. 컨셉은 **Trello 스타일 칸반 보드**. 내 안의 기획자가 "이거 ScriptableObject로 데이터 구조 잡으면 되겠는데?" 하고 속삭였지만 참았다. 여긴 웹이다.

```
TODO         IN PROGRESS      DONE
─────────    ─────────────    ─────
[프로젝트1]  [프로젝트3]      [프로젝트5]
[프로젝트2]                   [프로젝트6]
```

컬럼 3개, 프로젝트 카드가 각 컬럼에 들어간다. 드래그 앤 드롭은 나중에 구현하기로 하고, 일단은 **상태 선택박스(select)**로 이동하게 만들었다. 드래그 앤 드롭 라이브러리를 설치하면 번들 사이즈 커지는 게 싫어서. 유니티에서도 EventSystem 하나 깔면 성능 이슈 생기잖아? 같은 맥락이다. (아닌가?) 패키지 매니저에서 쓸데없는 패키지 설치했다가 빌드 사이즈 100MB 늘어난 트라우마가 아직 안 갔다.

### AdminDashboard.jsx 구조

```jsx
const AdminDashboard = ({ onExit }) => {
  const [projects, setProjects] = useState(loadProjects);
  const [showModal, setShowModal] = useState(false);
  const [editingProject, setEditingProject] = useState(null);
  // ...
};
```

상태가 3개. `projects`는 프로젝트 목록, `showModal`은 프로젝트 추가/수정 모달, `editingProject`는 현재 수정 중인 프로젝트. 유니티의 GameManager에서 여러 서브 매니저 참조하는 것과 비슷한데, React는 그냥 `useState` 하나씩 선언하면 끝이다. 간단해. `[SerializeField] private` 붙이고 인스펙터에서 드래그 앤 드롭으로 참조 걸어주는 그 노가다가 없다니. 눈물이 좀 난다.

### CRUD 기능

**Create**: `[ NEW PROJECT ]` 버튼 클릭 → 모달 오픈 → 폼 작성 → 저장

```jsx
const handleSaveProject = (projectData) => {
  if (editingProject) {
    setProjects(projects.map(p => 
      p.id === editingProject.id ? { ...projectData, id: p.id } : p
    ));
  } else {
    const newProject = { ...projectData, id: Date.now() };
    setProjects([...projects, newProject]);
  }
};
```

`Date.now()`를 ID로 쓴다. 유니티에서 `System.Guid.NewGuid()` 쓰는 것과 같은 느낌인데, 훨씬 간단하다. 게다가 애초에 로컬에서만 쓸 거라 중복 걱정도 없고. `GetInstanceID()` 쓰다가 런타임에 꼬여본 사람만 이 해방감을 안다.

**Read**: `projects.filter(p => p.status === column.id)` 로 상태별 필터링. LINQ의 `.Where()`가 그리워질 줄 알았는데, `.filter()`도 나름 괜찮다. `System.Linq` 안 써도 되는 세상이라니.

**Update**: 프로젝트 카드의 Edit 버튼 클릭 → 기존 데이터로 모달 열기 → 수정 → 저장.

**Delete**: `window.confirm('DELETE THIS PROJECT?')` → 확인하면 `projects.filter`로 제거.

`window.confirm`... 이거 웹에서도 쓰는 거구나. 유니티에서 `EditorUtility.DisplayDialog` 쓰는 것과 같다. 근데 게임 런타임에서는 못 쓰니까 직접 다이얼로그 UI 만들어야 했는데, 웹은 브라우저가 알아서 해준다. 편하다. Prefab 만들고 Canvas 위에 올리고 `DOTween`으로 페이드 애니메이션 넣고... 그 30분짜리 작업이 한 줄이라니. 이게 문명의 차이인가.

## 🌪️ Scene 4 : LocalStorage (데이터가 날아가면 그건 존재하지 않았던 것)

Admin 대시보드에서 프로젝트를 추가하고 나서 새로고침하면... **데이터가 날아갔다.** `Destroy(gameObject)` 당한 느낌이었다. 아무도 호출하지 않았는데.

당연하다. React의 `useState`는 런타임 메모리에만 저장되니까. 유니티에서 `PlayerPrefs` 안 쓰고 그냥 변수에만 저장하면 씬 전환할 때 날아가는 것과 똑같다. `static` 변수에 넣어둬도 도메인 리로드 한 방이면 전부 `GC.Collect()` 당하는 그 허무함.

```javascript
const STORAGE_KEY = 'portfolio_projects';

const loadProjects = () => {
  try {
    const stored = localStorage.getItem(STORAGE_KEY);
    return stored ? JSON.parse(stored) : DEFAULT_PROJECTS;
  } catch {
    return DEFAULT_PROJECTS;
  }
};

const saveProjects = (projects) => {
  try {
    localStorage.setItem(STORAGE_KEY, JSON.stringify(projects));
  } catch (e) {
    console.error('Failed to save projects:', e);
  }
};
```

`localStorage.setItem` / `getItem`이 `PlayerPrefs.SetString` / `GetString` 같은 거다. JSON 직렬화해서 문자열로 저장하는 것도 유니티에서 데이터 저장할 때랑 똑같은 패턴. `JsonUtility.ToJson()` 해서 `PlayerPrefs`에 때려박는 그 패턴. 5년간 몸에 밴 근육 기억이 여기서 빛을 발한다.

그리고 `useEffect`로 `projects` 상태가 바뀔 때마다 자동 저장:

```jsx
useEffect(() => {
  saveProjects(projects);
}, [projects]);
```

이거 유니티에서 `OnApplicationPause`이나 `OnApplicationQuit`에서 `PlayerPrefs.Save()` 호출하는 것과 같은데, 훨씬 세밀하다. 상태가 바뀔 때마다 즉시 저장되니까. 유니티에서 이거 하려면 `ReactiveProperty` 같은 거 써야 하는데 여긴 프레임워크 레벨에서 지원해준다. 프레임워크의 복지 수준이 다르다.

## 🏰 Scene 5 : SECRET ROOM 테마 (빨간색은 항상 멋지다)

Admin 페이지를 녹색 테마로 하면... 그냥 포트폴리오랑 똑같잖아. 비밀의 방인데 말이야. `Material`을 바꿔야 분위기가 바뀌는 법이다.

**"Admin 대시보드는 빨간 계열 테마로 해줘. 비밀스러운 느낌으로."**

```css
.admin-container {
  background: linear-gradient(180deg, #0a0505 0%, #0d0808 100%);
}

.admin-title {
  color: #ff4444;
  text-shadow: 0 0 10px rgba(255, 68, 68, 0.5);
}
```

짜잔. 어두운 붉은 배경에 형광 빨간 글씨. 완전히 다른 분위기가 된다. 마치 폴아웃에서 Vault-Tec 터미널에서 Enclave 터미널로 넘어간 느낌? (Enclave가 빨간색이었나? 기억이 가물가물한데, 아무튼 비밀조직 느낌이면 된다.) URP에서 Post Processing Volume 하나 얹었더니 갑자기 호러 게임이 되는 그 느낌과 비슷하다.

버튼도 전부 빨간 테마. EXIT 버튼은 약간 어두운 빨간색(#aa3333)으로, 긴장감을 유발한다. "여기서 나가고 싶어?" 같은 느낌. `Application.Quit()` 버튼에 빨간색 넣으면 유저가 누르기 전에 한 번 더 생각하는 그 효과.

그리고 상태별 색상도 지정했다:

```css
.status-todo { color: #ffaa00; }       /* 주황 - 아직 안 시작 */
.status-in_progress { color: #ffff44; } /* 노랑 - 진행 중 */
.status-done { color: #66ff66; }       /* 초록 - 완료 */
```

선택박스(`<select>`)의 배경이 흰색으로 나오는 문제도 있었다. 다크모드인데 드롭다운만 눈부시게 하얗게 빛나고 있었다. 눈이 아팠다. 눈물이 날 뻔했다. `Bloom` 이펙트를 눈에 직접 쏘는 수준이었다.

```css
.status-select option {
  background: #1a0808; /* 어두운 붉은 배경 */
  color: #ff6666;
}
```

`<option>` 태그는 브라우저별로 스타일 제한이 있어서 완벽하게 컨트롤하기 어렵다. 유니티의 Dropdown 컴포넌트에서 템플릿 수정하는 것처럼 자유도가 높지 않다. 브라우저가 만든 렌더링 엔진 위에서 우리가 놀고 있는 거니까 어쩔 수 없지. 이건 렌더 파이프라인을 못 바꾸는 것과 같다. Built-in RP에서 셰이더 커스텀하려다가 "이건 SRP에서만 됩니다" 듣는 그 좌절감과 일맥상통한다.

## 💀 Scene 6 : 모달 가독성 개선 (초록색 안경을 벗고)

PROJECT DETAILS 모달을 열었는데... **전부 초록색이었다.** 제목도 초록, 설명도 초록, 태그도 초록, 피처도 초록. CRT 모니터에 초록 안경을 끼고 보는 것 같았다. `Debug.Log`를 콘솔 창에서 200개쯤 보다 보면 눈이 초록색으로 물드는 그 현상과 비슷했다.

시각적 계층이 없으니까 뭐가 중요한지 모르겠다. 텍스트가 서로 섞여 보인다. 유니티 UI에서 전부 같은 폰트 사이즈 + 같은 색상으로 UI 구성하면 가독성이 개판이 되는 것과 똑같은 문제다. 인스펙터에서 `[Header]` 어트리뷰트 안 쓰고 변수 50개를 쭉 나열한 컴포넌트를 보는 기분이었다.

**색상 계층화:**

| 요소 | 색상 | 비유 |
|------|------|------|
| 제목/값 | `#33ff66` (밝은 초록) | 게임에서 강조 텍스트 |
| 레이블 | `#66aa88` (어두운 초록) | NPC 이름 |
| 설명 | `#aaccbb` (회색 초록) | 일반 대사 |
| Features | `#99ddbb` (연한 초록) | 보상 텍스트 |

그리고 오늘 깨달은 게 있다.

**웹 개발은 결국 UI 개발이다.**

유니티에서 UI 만들 때 느꼈던 그 고통과 성취감이 그대로 여기에도 있다. 레이아웃이 안 맞아서 머리 싸매는 것도 같고, 색상 하나 바꿨는데 전체 분위기가 확 바뀌는 쾌감도 같다. 다만 React는 유니티보다 **"상태 관리"**라는 개념이 훨씬 직관적이게 느껴진다. `useState` 하나로 UI 업데이트가 끝나니까. 유니티에서 `OnValidate`, `OnInspectorGUI`, `UnityEvent.AddListener` 이리저리 꼬아야 하는 것보다 훨씬 깔끔하다. 5년간 `SerializedProperty`랑 `CustomEditor` 지옥에서 살다가 해방된 기분.

아, 그리고 **ESLint** 때문에 커밋을 3번이나 고쳤다. `motion.div`의 `motion`을 unused variable로 잡는 거 보고 10분 동안 뭐가 문제인지 몰랐다. 결국 `varsIgnorePattern` 정규식을 수정해서 해결. 웹 개발에서도 린터(Linter)는 나의 적이자 동료다. 유니티에서 컴파일 에러 잡는 것과 같은 그 러브헤이트 관계. `CS0219: The variable is assigned but its value is never used` — 이 경고 메시지가 웹에서도 나를 따라오다니. 전생에 변수를 선언만 하고 안 쓴 죄를 지었나 보다.
